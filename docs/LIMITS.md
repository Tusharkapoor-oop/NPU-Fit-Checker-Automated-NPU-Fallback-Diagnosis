# NPU Fit Checker — Limitations & Scope

This document details the boundaries, experimental scope, and design limits of NPU Fit Checker. Every limit is stated transparently to maintain absolute engineering honesty.

---

## 1. Validated on One Model Family, Designed to Generalize
- **Current Validation**: The rule engine and profile parser have been validated against **MobileNetV2** (torchvision weights `DEFAULT`, 224×224, batch size 1) across both FP32 and INT8 QDQ configurations.
- **Genuine Unsupported Operators**: The test suite and real-hardware profiles have **not yet been tested against a model with a genuinely unsupported operator** (e.g., complex non-standard activations, 5D+ tensors, or custom C++ operators). On MobileNetV2, 100% of internal neural network layers are supported by Qualcomm's Hexagon NPU backend.
- **Generalization Design**: The parser and rule engine are built on standard ONNX operator semantics and Qualcomm AI Hub execution schemas (`execution_summary`, `execution_detail`), designed to generalize across standard vision and transformer architectures once profiled.

## 2. Cloud Device Only (No Physical HP Hardware)
- **Execution Target**: All profiling and hardware metrics were gathered exclusively on **Qualcomm AI Hub's cloud-hosted Snapdragon compute devices**:
  - Primary: **Snapdragon X2 Elite CRD** (`sc8480xp`, Hexagon v81 DSP, Windows 11)
  - Secondary: **Snapdragon X Elite CRD** (`sc8380xp`, Hexagon v73 DSP, Windows 11)
- **No Physical Hardware**: No physical HP hardware (e.g., HP OmniBook X, HP EliteBook, or physical on-premise Snapdragon laptops) was used or accessed. All device interactions use the cloud Workbench API (`qai-hub`).

## 3. Rules are Pattern-Based, Not ML-Based
- **Deterministic Rules**: The diagnostic engine (`fitchecker/rules.py`) uses deterministic, rule-based pattern matching on the execution profile data:
  - Detection of compute unit allocation (`compute_unit == "CPU"` vs `"NPU"`)
  - Boundary operator pattern recognition (`QuantizeLinear` / `DequantizeLinear` named `QcQuantizeOp_*`)
  - Latency and compute-unit fraction threshold checks
- **No Learned Classifier**: The tool does not use a neural network or machine learning model to predict fallbacks. Fallbacks are diagnosed directly from empirical hardware execution reports generated by Qualcomm's compiler.

## 4. Boundary QDQ Classification Tested on One Architecture
- **Boundary Adapter Pattern**: The rule distinguishing expected boundary adapters (`QcQuantizeOp_input_q` and `QcQuantizeOp_output_dq`) from erroneous fallbacks was verified on MobileNetV2's QDQ graph.
- **Other Quantization Schemes**: Models quantized using non-standard QDQ placements, custom scale/zero-point tensor placements, or per-channel weight adapters across unsupported subgraphs may require pattern updates.

## 5. Static Input Shapes Only
- **Fixed Dimensions**: Profiles were executed with static input tensors `[1, 3, 224, 224]`.
- **Dynamic Shapes**: Models requiring dynamic axes (e.g., variable sequence lengths in LLMs or dynamic batching) were not evaluated and typically require shape freezing or profile-specific compilation options on Qualcomm Hexagon NPU.

## 6. Execution Schema Compatibility
- **Target Schema**: The parser relies on Qualcomm AI Hub's confirmed schema (`execution_summary` containing `estimated_inference_time` in microseconds, and `execution_detail` containing layer-by-layer `name`, `type`, `compute_unit`, `execution_time`, `execution_cycles`).
- If a future AI Hub API changes this structure, the built-in schema guard prevents false analysis and halts with a schema error.
